# 워크플로우 & FAQ

실제로 자주 쓰는 패턴과, 막혔을 때 볼 것들입니다.

## 자주 쓰는 워크플로우

### 개발 진행 확인 — 작업 그래프

**Runner 설치 없이 로컬에서 기존 작업의 관계와 진행 상태를 확인합니다.**

1. 사이드바 **작업 그래프**를 열고 프로젝트를 선택합니다.
2. 기존 작업이 노드로 표시됩니다. 실행 중·검토 대기·완료·실패는 기존 작업 목록이 갱신될 때 함께 바뀝니다. 검토 대기는 완료 수에 포함하지 않습니다.
3. 노드를 선택해 **Phase**를 지정하거나 새 Phase를 추가합니다. Phase별 완료 수를 함께 확인할 수 있습니다.
4. 필요하면 **선행 작업 선택 → 연결**로 관계를 표시합니다. 순환을 만드는 연결은 선택할 수 없습니다. **해제**는 관계 표시만 지웁니다.
5. **작업 열기**로 해당 작업의 기존 대화·결과 화면으로 이동합니다.

실선은 사용자가 지정한 선행 관계이고, 점선은 기존 작업의 **이어받음** 기록입니다.
Phase와 선행 관계는 자동 추론하지 않으며 이 앱의 로컬 저장소에 호스트·프로젝트별로 저장합니다.
상태의 기준은 Praxis 작업 목록입니다. 코드나 계획 문서를 분석해 개발 완료율을 추정하지 않습니다.
관계 표시는 실행 순서나 작업 상태를 변경하지 않습니다.

연결이 끊겼으면 마지막 확인 상태로 표시하고 현재 진행·완료 수에서 제외합니다.
그래프 사용을 위해 별도 실행 환경을 구성할 필요는 없습니다.

구현 현황과 검증 범위를 참고하세요.

### A. 평범한 기능 수정 — 기본형

```
컴포저에 지시문 → 작업 생성 → (기다림) → AwaitingReview 알림 → Diff 확인 → Approve
```

가장 많이 쓰는 흐름입니다. 대부분 여기서 끝납니다. 요령 하나 — **지시문에 "테스트도 같이
고쳐줘"를 넣으면** 검토할 때 훨씬 편합니다.

### B. 병렬로 여러 개 돌리기

작업 하나를 띄워 놓고 기다릴 필요가 없습니다. 서로 다른 파일을 건드리는 작업이라면 3~4개를
동시에 띄워 두고, 끝나는 순서대로 검토하면 됩니다.

**주의** — 같은 파일을 건드릴 작업 여러 개를 동시에 돌리면, 먼저 승인한 쪽이 머지된 뒤 나머지가
충돌할 수 있습니다. 겹칠 것 같으면 순서대로 하세요.

### C. 접근법이 여러 개일 때 — 앙상블

"A로 할지 B로 할지 모르겠다" 싶으면 여러 에이전트에게 같은 일을 시키고 결과를 비교합니다.

```
앙상블 실행 → 결과 매트릭스로 나란히 보기 → 심사 → 나은 쪽 채택
```

시간과 토큰을 더 쓰지만, 설계 방향이 갈리는 작업에서는 값을 합니다.

### D. 요구사항이 애매할 때 — 인터뷰

지시문을 쓰다가 "내가 뭘 원하는지 나도 잘 모르겠다" 싶으면 먼저 다듬습니다.

- 빠르게 정리하고 싶다 → 인터뷰 패널에서 **"채점만"**(객관식으로 부족한 부분을 채움)
- 깊게 파고 싶다 → **1단계 "깊게 파기"**(주관식 질문을 하나씩 던짐) 후 "지시문에 적용 → 채점"

애매한 지시문으로 에이전트를 돌리면 애매한 결과가 나옵니다. 여기서 5분 쓰는 게 검토에서
30분 아낍니다.

### E. 같은 지시를 반복할 때 — 스킬

"릴리스 노트 정리", "테스트 커버리지 확인"처럼 매번 비슷하게 쓰는 지시문은 스킬로 만듭니다.

```
.praxis/skills/release-note.md 작성 → 컴포저에서 /release-note 호출
```

전역(`~/.praxis`)에 두면 모든 프로젝트에서 쓸 수 있고, 프로젝트 쪽이 우선합니다.
GitHub에서 남의 스킬을 가져올 수도 있습니다.

### F. 자리를 비울 때 — 모바일 PWA

긴 작업을 돌려놓고 나갈 거라면 모바일 PWA를 붙여 두세요(설정 > 모바일). 작업이 검토 대기나
질문 대기로 바뀌면 Web Push 알림이 오고, 폰에서 상태를 보고 대화·승인·폐기까지 할 수
있습니다. 밖으로는 tailnet 경유로만 열립니다.

> 전에 있던 텔레그램 채널은 2026-09-13에 제거됐습니다 — 이 PWA가 그 자리를 대신합니다.

### G. UI를 건드릴 때 — 디자인 모드

"이 여백이 어색해"를 말로 설명하기 어려우면 캡처해서 넘깁니다. 프리뷰나 에디터 영역을 잡아
프롬프트에 붙이면 에이전트가 이미지를 같이 봅니다.

## FAQ

### 작업 만들 때

**Q. "동시 실행 한도에 도달" 하고 작업이 안 만들어집니다.**
기본 8개가 상한입니다. 대기열에 쌓이는 게 아니라 **그 자리에서 거부**됩니다. 진행 중인 작업을
승인하거나 폐기해서 자리를 비우세요. 설정에서 상한을 올릴 수 있습니다(1~64). 다만 동시에
많이 돌리면 검토가 밀려서 오히려 느려집니다.

**Q. 에이전트 CLI를 못 찾는다고 합니다.**
Praxis는 CLI를 대신 설치하지 않습니다. 터미널에서 `claude` / `codex` / `agy`가 정상 동작하는지
먼저 확인하세요. 터미널에서 안 되면 Praxis에서도 안 됩니다. 설치는 됐는데 앱에서만 못 찾는다면
PATH 문제일 가능성이 큽니다.

**Q. "워크트리 격리"를 꺼야 할 때는 언제인가요?**
거의 없습니다. 격리를 끄면 에이전트가 **원본 레포에서 직접** 작업하므로 폐기로 되돌릴 수
없습니다. 빌드 산출물이나 로컬 전용 파일이 꼭 필요한 경우에만 쓰고, 그때도 커밋되지 않은
변경이 없는 상태에서 시작하세요.

### 작업 도중

**Q. 작업 중에 앱을 닫으면 어떻게 되나요?**
실행 중이던 에이전트 프로세스는 정리됩니다. 다시 열면 그 작업은 `Failed`로 표시됩니다.
worktree와 그때까지의 변경은 남아 있으므로, 내용을 확인하고 이어서 지시하거나 폐기하면 됩니다.

**Q. 에이전트가 엉뚱한 방향으로 가고 있습니다.**
그냥 폐기하세요. worktree째 사라지고 원본은 그대로입니다. 이게 격리 실행의 핵심입니다 —
**되돌리는 비용이 0이라 과감하게 시켜 볼 수 있습니다.**

**Q. 에이전트가 고친 파일을 제가 직접 수정해도 되나요?**
됩니다. 다만 에이전트가 도는 중에 같은 파일을 건드리면 저장할 때 외부 변경 경고가 뜹니다.
가급적 작업이 끝난 뒤 검토 단계에서 손보세요.

### 승인할 때

**Q. 작업을 시작한 뒤 원본 레포를 다른 브랜치로 옮겼습니다. 승인 대상도 바뀌나요?**
아닙니다. 격리 실행의 승인 대상은 작업에 저장된 시작 브랜치입니다. 검토 화면의
`머지 대상`을 확인하세요. 원본이 다른 브랜치에 있으면 승인 전용 worktree에서 병합하며,
원본의 브랜치나 미커밋 변경을 자동 전환·보관하지 않습니다.

대상 브랜치가 다른 worktree에서 사용 중이면 그 위치를 안내합니다. 해당 작업을 정리해
브랜치 점유를 해제한 뒤 재승인하세요. 대상 브랜치가 삭제됐거나, 대상 체크아웃에
미커밋 변경·진행 중인 Git 연산이 있으면 이를 먼저 해결해야 합니다.

**Q. 승인했는데 충돌이 났습니다.**
Praxis가 자동으로 머지를 되돌리고 알려 줍니다. **원본 브랜치가 충돌 상태로 방치되는 일은
없습니다.** 충돌 해소 기능으로 worktree 안에서 base를 역방향 머지해 풀고 나서 다시 승인하세요.

**Q. 변경 중 일부만 받고 싶습니다.**
부분 적용을 쓰세요. Diff에서 원하는 hunk만 골라 적용할 수 있습니다.

**Q. 승인 버튼을 두 번 눌렀습니다.**
괜찮습니다. `AwaitingReview → Finalizing` 전이가 단독 점유로 잠기기 때문에 중복 승인은
구조적으로 불가능합니다.

### 메모리·지식

**Q. 메모리가 제 컨텍스트 파일을 덮어쓰나요?**
아니요. worktree 쪽 `AGENTS.md`에 **마커로 둘러싼 블록**만 넣습니다. 원본 레포의 파일은
건드리지 않습니다. 옛 worktree의 `CLAUDE.md`·`GEMINI.md`에 남은 블록은 거둬지기만 합니다.

**Q. 이상한 메모리가 쌓입니다.**
자동 수집된 후보는 **승인해야만** 실제로 반영됩니다. 메모리 화면에서 거르세요. 이미 들어간
것은 삭제하거나 이전 버전으로 되돌릴 수 있습니다.

### 음성

**Q. 음성 입력이 동작하지 않습니다.**
STT 서버를 따로 띄워야 합니다. Praxis는 전사 서버를 내장하지 않고, OpenAI 호환
`/audio/transcriptions` 주소를 부를 뿐입니다. 설정에서 주소를 넣고 **연결 테스트**를 돌려
보세요 — 실제로 왕복해 보기 때문에 여기서 통과하면 실사용도 됩니다.

**Q. 녹음이 중간에 끊깁니다.**
60초가 상한입니다. 거기까지만 전사됩니다.

**Q. 원격 Runner는 어떻게 연결하나요?**
지금은 연결할 수 없습니다. 설정 › 연결의 Remote Runner는 2026-09-19에 제거됐고, 작업은
전부 이 기계에서 돕니다. 저장소의 Runner 바이너리·설치 스크립트는 남아 있지만 앱이 붙지 않습니다.

### 설치

**Q. SmartScreen 경고가 뜹니다.**
코드 서명 전이라 정상입니다. **추가 정보 → 실행**으로 진행하세요. 파일이 맞는지 확인하려면
Release의 `SHA256SUMS.txt`와 대조하면 됩니다.

**Q. 내려받을 설치 파일은 어디 있나요?**
아직 게시된 릴리스가 없습니다. 지금은 소스에서 `npm run tauri build`로 직접 빌드해야 합니다.
반복 빌드·검증이 이뤄진 환경은 macOS(Apple Silicon)입니다.

## 문제가 계속될 때

작업 상태와 재현 절차를 정리해 개발자에게 전달하세요. 다음이 있으면 훨씬 빠릅니다:

- 작업 ID와 상태(`Running` / `AwaitingReview` / `Failed` 등)
- 사용한 에이전트 벤더
- 터미널 도크에 남은 마지막 출력
